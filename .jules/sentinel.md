## 2025-02-27 - Password Hashing Migration and Constant-Time Comparison
**Vulnerability:** Admin passwords were created and stored in plaintext (`changeme`) in the database, and checked using standard equality operators (`==`, `!=`). This risks catastrophic credential compromise if the database is accessed, and standard equality allows timing attacks when verifying passwords.
**Learning:** Security fixes that replace plaintext with hashing often need to preserve backward compatibility so existing systems/users do not immediately break. By inspecting the structural format of the password string (`len() == 97` and a `$` delimiter), the app can dynamically determine if a stored password is a hash or legacy plaintext, allowing for an automatic, seamless upgrade path on the next password change. Additionally, `secrets.compare_digest` must be used universally to prevent timing attacks.
**Prevention:** Future authentication setups must use strong cryptographic algorithms like PBKDF2, bcrypt, or Argon2 by default on day zero. Standard equality checks must never be used for sensitive strings like passwords or hashes; always rely on `secrets.compare_digest`.
